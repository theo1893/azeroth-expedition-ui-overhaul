# 候选资产审查清单

按下列顺序审查。前一层存在致命问题时先给出退回结论，不要用 Alpha 清理、
锐化或追加装饰掩盖结构错误。

## 自主修复循环判定

- 对最多 `5` 次实际 ImageGen 生图／修图中的每个输出，都从第 1 项重新执行完整清单；
  不得因为前一版通过某项就跳过本版的语义、结构或美术检查。
- 任一客观合同门禁失败时，本次不得进入用户复审。记录第一失败门禁、必须
  保持的正确区域和下一次具体修复，再在同一授权边界内编辑或重生。
- 相同首要失败连续出现时必须改变修复策略，不能用相同正文反复抽卡。
- 只有全部客观门禁通过，或剩余判断纯属用户审美取舍时，才能提前结束循环并
  标记 `candidate-reviewed / P3`。
- 第 `5` 次仍有客观失败时标记
  `candidate-rejected / repair-budget-exhausted`，停止调用并把五次证据交给
  用户；内部通过仍不等于用户接受。

## 0. 执行正文与传输一致性

- 本次调用是否使用已提交的完整授权正文或完整 `.rN` 正文，而不是差异摘要？
- 实际上传图、输入顺序和职责是否与 work 一致，是否意外加入旧失败稿？
- 提示词是否发生截断、编码损坏或段落丢失？若仍产生了候选图或 provider
  result，本次不可用但计入实际生图预算；若在生成前即失败且没有任何生成
  证据，则作为流程错误单列，不占 `0/5`。
- 无候选的流程错误不进入后续视觉门禁，也不创建 `.rN`；先记录 session、
  错误、生成证据缺失和针对性修复，再以同一已提交正文重试。
- 若执行器报告 revised prompt，是否已完整记录？候选仍必须按用户授权正文的
  全部门禁审查，不能因为 revised prompt 省略某项就降低验收标准。

## 1. 范围与对象身份

- 是否只包含合同中的组件和状态？
- 每个区域能否对应明确的 pfUI、Blizzard 或外部 provider 对象？
- 是否把动态文字、图标、任务行、按钮、滚动条或固定槽位错误烘焙进背景？
- 是否漏掉独立交互状态，或把多个运行时对象画成不可拆的一张图？

失败示例：把整张任务日志绘成一个背景；把需求、贪婪、放弃三个按钮烘焙在
拾取面板里；用视觉上像按钮的装饰代替未知 provider 对象。

## 2. 语义、解剖与物理逻辑

- 物件的观察方向、内外关系、开合／翻页／滑动空间是否成立？
- 承重、连接、铰接、装订、卷曲和重叠是否符合物理结构？
- 可运动部件是否被装饰压死？
- 对称、近等宽、中心线或偏置是否来自真实结构，而非误用文字安全区比例？

这是最高优先级。连通区数量、尺寸和透明度不能证明一本书能翻页、一个拉环能
拉动或一个按钮属于正确层级。

## 3. 透视、图层与轮廓

- 所有部件是否共享观察角度、光源、厚度和尺度？
- z-order 是否与 runtime 装配一致？
- 接缝和阴影是上下层关系的结果，还是被平涂在同一平面？
- 轮廓是否保留香草魔兽原型和交互习惯？

必须制作一次按真实层序的离线重组。图集排版只证明“有这些块”，不证明它们
能正确装回游戏。

## 4. 美术一致性

- work 是否链接每张 `assets/locked/` 基准对应的模块／子模块基线 Prompt，
  而不是只上传图片？
- 提示词是否逐项记录“必须继承、组件级转译、明确排除、冲突裁决”，并把这些
  约束写入实际执行正文？
- 是否遵循 `assets/locked/`、其 Prompt provenance、模块
  `ART_BASELINE.md`／`SUBMODULE_ART_BASELINES.md` 和
  `docs/GLOBAL_ART_BASELINE.md`？
- 是否把 `assets/source/` 派生母版错误提升为高于锁定基准的视觉权威？
- 是否保持香草时代的手绘轮廓、厚重材料与有限高光？
- 是否出现现代 HUD 语言：半透明黑玻璃、细金线、规则卡片、扁平矩形、
  霓虹常亮、暗黑 3 式尖冠或精密机械面板？
- 同批对象的纸张、皮革、黄铜、木材、磨损、阴影和色温是否一致？
- 小尺寸下装饰是否压过信息层？

视觉审查必须同时对照锁定图和从原始提示词提取的美术 DNA。候选与某张派生
source 相似，不代表它保持了锁定基准的物件身份、绘制手法或年代感。

## 5. 组件合同与状态

- 对象数量和状态数量是否逐项匹配合同？
- 状态差异是否表达交互语义，而不是只做无意义调色？
- 点击几何、文字安全区、图标安全区是否仍可用？
- 端帽、铆钉、缝线、页角和符号是否被放在不可拉伸区域？
- 连续纹理能否无跳点平铺？三段式／九宫格边界是否有足够缓冲？

## 6. 裁切、拉伸与装配

至少检查：

1. 原始尺寸和 100% runtime 尺寸。
2. 合同中的最小、基准、最大尺寸。
3. 实际 z-order 和透明混合。
4. 文字、图标和交互对象的安全区。
5. 重复中段的接缝、节奏和边缘防渗色。
6. 与相邻已接受资产的材质、厚度和光照衔接。
7. 真实 Frame 像素几何、裁切与当前最新的 accepted/runtime UI。
8. 真实对象数量与代表性最高／常见信息密度；动态文字、图标、数值和状态
   分布必须接近游戏，而不是只摆少量样例。

每次 generate 或 edit 后都必须重新生成 `100%` runtime 尺寸的真实排版预演，
并在进入内部通过或用户复审前目视检查。重复组件必须实例化真实重复数量；
例如 23 行 Quest Log 资产要覆盖全部 23 个行槽并使用真实任务排版。contact
sheet、稀疏演示、调试网格或孤立组件板不能代替真实排版预演。

未完成的相邻组件优先显示当前真实 fallback；只能在无法取得 fallback 时使用
简化占位，并在 work／manifest 中明确其非权威范围，不能让用户误以为占位
已经接受或接入。

预演图只进入 `generated/`。不要把合成预演误当作源资产。

## 7. 技术像素检查

- 文件格式、像素尺寸和色彩模式。
- SHA-256。
- 全透明、半透明、不透明像素数量。
- 可见像素包围盒及是否触碰 atlas 单元边缘。
- 可见 `#00FF00` 或强绿色残留。
- 对象间透明隔离和至少 4px 防渗色边距。

可使用 `scripts/inspect_candidate.py`。它的数值是证据，不是综合色觉结论。
“五个连通区”不能证明合同中的五个对象都正确。

## 8. 用户复审包

给用户展示最少但充分的证据：

- 候选原貌或透明棋盘底预览；
- 按真实层序、`100%` 游戏尺寸、真实对象数量和现实信息密度生成的真实排版
  预演；必须叠加当前最新的新 UI；
- 若修订只改变局部，提供旧／新并排或清晰标注差异；
- 简短说明对象数量、已通过门禁、仍需用户判断的美术问题。

不要把调试网格、切片标签和尺寸文字烘焙进候选本身。

## 判定格式

审查结果按以下顺序表述：

1. `通过`、`有条件通过` 或 `退回`。
2. 当前子状态与最高项目阶段。
3. 第一个失败门禁及其可观察证据。
4. 次要问题。
5. 下一版必须改变和必须保持的内容。
6. 是否允许进入用户复审、`assets/source/` 或 runtime。

若退回，修订指令必须具体到对象、方向、层级、比例、遮挡、可运动空间或切片
规则；美术问题必须回指具体继承条款，避免只写“更厚重”“更像香草”。
